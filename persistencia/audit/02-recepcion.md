## Hallazgos críticos

**H1 — No existe el consecutivo de recepción (CO-26-02-169).**
Es el identificador operativo central del negocio actual: se imprime en la etiqueta, se usa para buscar en garantía, para la orden de servicio y para el despacho. En el repo el `id` del registro es `` `${prefix}-${Date.now()}-${random}` `` (`crm-prospect-equipment-modal.component.ts:3526`) y el "shortCode" del QR son los últimos 6+4 caracteres de esos UUIDs (`equipment-qr.util.ts:10-14`). En backend no hay columna `code`/`consecutive` ni secuencia (`migrations_crm_equipment_quotes.go:5-37`); la única secuencia del sistema es `remission_sequences`, para remisiones. Los `CO260206`, `CO260211`, `CO260315`… que aparecen en la UI son **datos mock** hardcodeados en `projects/services/project.service.ts:684-999`.

**H2 — Las fotos de ingreso se guardan como miniatura, no como archivo original.**
El propio código lo declara: `crm-prospect-equipment.store.ts:31-34` ("The frontend currently stores only the evidence snapshot needed for demos: thumbnail + EXIF summary + file hash. The API should receive the original binary") y `modal:1866` ("The current frontend-only version only keeps thumbnail + metadata"). El campo `backendSyncStatus` admite `"frontend-only" | "pending-upload" | "uploaded"` (`store.ts:56`) pero nada lo mueve de `frontend-only`. Esto rompe el caso de uso que Maribel describió como crítico: *"un cliente dice que él mandó un equipo con este conector y que nosotros se lo devolvimos sin el conector… yo voy y miro las fotos del ingreso"* (`@43:30`) — una miniatura no prueba nada en una disputa.

**H3 — Los maestros de recepción viven en `localStorage`, no en la base de datos.**
Familias, modelos industriales, tipos de servicio y ubicaciones están en `company-equipment-config.store.ts` (clave `adminux.company.equipment.catalog.v1`, línea 44) con valores por defecto hardcodeados (`:46, :70, :106, :137`). Consecuencias: (a) cada navegador/PC de la recepción tiene su propio catálogo; (b) el componente de administración `company-equipment-config.component.ts` (964 líneas) **no tiene ruta registrada** en ningún `*.routes.ts`, o sea es inaccesible; (c) la clasificación automática por familias y el autorrelleno por tipo (items 16 y 17) dependen de datos que no son compartidos. El backend sí tiene un mecanismo de catálogos funcionando (`crm/handler.go:36-40`, `crm/service.go:60-74`) que no se está usando para esto.

**H4 — Doble fuente de verdad: API + `localStorage` en paralelo.**
`crm-prospect-equipment.store.ts:275` define `STORAGE_KEY = "adminux.crm.prospect-equipment-records"` con lectura/escritura completa (`:667, :688`). El flujo principal ya usa la API, pero siguen leyendo del `localStorage`:
- `dashboard.component.ts:15, 1654` → los KPI "equipos pendientes por facturar / listos para facturar / en proceso" salen de `getAllProspectEquipmentItems()` (localStorage), **no** de la API. El panel que Maribel pidió como su vista de control muestra datos que no existen en el servidor.
- `projects/services/project-equipment.service.ts:102, 122` → el kanban busca y actualiza el estado del equipo en localStorage y recién después sincroniza con la API (`:130`).
- `company-equipment-config.component.ts:751, 802, 904` → reasignación y conteo de equipos por ubicación contra localStorage.

**H5 — El estado de garantía se captura y se descarta.**
`oldCode`, `firstReceptionDate` y `warrantyMonths` viven únicamente en un `Map` del componente (`warrantyStateByItemId`, `modal:126-129, 1765`). No están en `ProspectEquipmentItem` (`store.ts:74-116`) ni en `backend/internal/crm/equipment/types.go`. Al recargar la página o reabrir la recepción, la marca "Es garantía", el código anterior y los meses de garantía desaparecen. `findPreviousReception` (`warranty.logic.ts:88-127`) sí reconstruye la recepción anterior por serie/identificador, pero no devuelve el técnico, así que la regla *"se lo dejamos asignado a la misma persona que lo revisó la última vez"* no se puede cumplir.

**H6 — Sin permisos para el flujo de recepción.**
La ruta `/app/work-equipment-reception` no lleva ningún guard (`internal-layout.routes.ts:408-415`), en contraste con inventario que usa `inventoryPermissionGuard` + `data.inventoryPermission`. En backend, `defaultModules()` solo siembra `horarios`, `registro-horas`, `gastos-caja-menor` y `proveedores` (`acl/service_modules.go:83, 95, 110, 124`): no existe módulo de recepción en el ACL. La separación que describió Maribel —recepción registra pero **no** asigna, Giovanni asigna— no está modelada.

**H7 — El SLA configurable no persiste y no se consume.**
`GET/PUT /projects/sla-config` existe (`projects/handler.go:29-30`) pero el store es un mapa global en memoria: `var slaConfigStore = map[string][]SLAConfig{}` (`projects/service.go:368`) — se pierde en cada reinicio (el propio test `sla_config_test.go:9` lo documenta). La vista de recepción usa constantes propias (`work-teams.component.ts:32-33`) y nunca llama al endpoint.

**H8 — No hay envío de correos en todo el sistema.**
`grep -rn "smtp|SMTP|sendmail|SendMail|mailer" backend/` → **cero resultados**. Ninguna de las notificaciones pedidas (confirmación de recepción, aviso al técnico cuando un equipo vuelve en garantía, aviso de cotización) es posible hoy. Es un prerrequisito de infraestructura, no un detalle del módulo.
